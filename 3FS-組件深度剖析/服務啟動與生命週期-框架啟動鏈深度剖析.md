# 服務啟動與生命週期 — 框架啟動鏈深度剖析

> 對應原始碼：`src/common/app/`（`ApplicationBase` / `TwoPhaseApplication` / `OnePhaseApplication` / `Utils`）、`src/core/app/`（`ServerLauncher` / `MgmtdClientFetcher` / `ServerMgmtdClientFetcher`）、`src/common/net/`（`Server` / `ServiceGroup` / `Listener` / `ThreadPoolGroup`）
> 涵蓋進程：`mgmtd_main`、`meta_main`、`storage_main`、`monitor_collector_main`、`migration_main`、`simple_example_main`、`hf3fs_fuse_main`
> 風格基準：[`../3FS-元資料層深度剖析.md`](../3FS-元資料層深度剖析.md)
> 互補報告：[`simple_example_main` 報告](simple_example_main-服務框架最小範例深度剖析.md) 從「如何寫一個服務」的角度講同一套框架；本報告從「進程如何起來」的角度橫向拆解全部 binary。

## 0. 一句話總結

3FS 的每個服務 `main()` 都只有 7–9 行，把一個 Server 型別當模板參數丟給 `TwoPhaseApplication` 或 `OnePhaseApplication`，剩下全交給框架。這條啟動鏈要解決的核心問題只有一個：**一個進程在還不知道自己該用什麼配置的時候，怎麼把自己啟動起來。**

答案是把啟動切成兩段——先用本地的極簡「引導配置」建一個臨時的 mgmtd 連線，把真正的配置拉回來，然後**把引導設施整個丟掉**，用拉回來的配置建真正的服務。`TwoPhaseApplication` 這個名字就是字面意思。

最不顯而易見的三個點：

1. **`loadAppInfo` 必須排在 `initConfig` 之前**，因為 mgmtd 下發的不是配置而是**配置模板**，要用 appInfo 的欄位做變數替換（`Utils.cc:286`）。
2. **`setup()` 與 `start()` 的切分點在 `bind()` 之後、`accept()` 之前**，這個窗口讓 `beforeStart()` 能拿到真實監聽位址，也能做任意長的阻塞協調——storage 就在這裡無限迴圈等自己的 target 在叢集裡下線（`Components.cc:91`）。
3. **mgmtd 有自舉悖論**：它不能向自己拉配置，所以有一套獨立的 `MgmtdConfigFetcher` 直接讀 FDB，並且透過一個 `if constexpr` 分支把已建好的 kvEngine **移交**給 server，避免開兩份 FDB 連線（`ServerLauncher.h:62`、`MgmtdConfigFetcher.cc:52`）。

典型的一份（`src/meta/meta.cpp`，全文）：

```cpp
#include "common/app/TwoPhaseApplication.h"
#include "memory/common/OverrideCppNewDelete.h"
#include "meta/service/MetaServer.h"

int main(int argc, char *argv[]) {
  using namespace hf3fs;
  return TwoPhaseApplication<meta::server::MetaServer>().run(argc, argv);
```

三個 include 各自對應一件事：

- **`TwoPhaseApplication.h`** — 啟動框架。
- **`OverrideCppNewDelete.h`** — 全域覆寫 `operator new` / `operator delete`，接管整個進程的堆積分配。**必須在 `main.cpp` 而非任何 header 中 include**，因為它在全域作用域定義符號，每個連結單元只能有一份。詳見 [記憶體配置器包裝報告](memory_allocator_wrappers-記憶體配置器包裝深度剖析.md)。
- **Server 型別本身** — 框架靠它反向取出全部所需型別。

### 1.1 Server 型別作為「配置包」

`TwoPhaseApplication<Server>` 不用虛函式問 Server 要東西，而是在編譯期從 Server 的成員型別別名取（`TwoPhaseApplication.h:16-17`、`:25-27`）：

```cpp
using Launcher = typename Server::Launcher;
using ServerConfig = typename Server::Config;

struct Config : public ConfigBase<Config> {
  CONFIG_OBJ(common, typename Server::CommonConfig);
  CONFIG_OBJ(server, ServerConfig);
};
```

而 `Launcher` 自己又從 Server 取更多（`ServerLauncher.h:26-29`）：

```cpp
using AppConfig = typename Server::AppConfig;
using LauncherConfig = typename Server::LauncherConfig;
using RemoteConfigFetcher = typename Server::RemoteConfigFetcher;
static constexpr auto kNodeType = Server::kNodeType;
```

所以一個 Server 類別必須提供這一組「接線點」。以 `MetaServer.h` / `StorageServer.h:24-35` / `MgmtdServer.h:16-24` 對照：

| 接線點 | 意義 | mgmtd | meta / storage / simple_example |
|---|---|---|---|
| `kName` | 日誌與監控的服務名 | `"Mgmtd"` | `"Meta"` / `"Storage"` / `"SimpleExample"` |
| `kNodeType` | 向 mgmtd 索取哪一類配置 | `MGMTD` | `META` / `STORAGE` / `CLIENT` |
| `AppConfig` | 「我是誰」（nodeId） | `core::ServerAppConfig` | 同左 |
| `LauncherConfig` | 「怎麼找到 mgmtd」 | `MgmtdLauncherConfig` | `core::ServerLauncherConfig` |
| `RemoteConfigFetcher` | 「去哪拿配置」 | **`MgmtdConfigFetcher`** | `core::launcher::ServerMgmtdClientFetcher` |
| `CommonConfig` | log / monitor / memory | `ApplicationBase::Config` | 同左（simple_example 覆寫了預設值） |

**唯一的差異落在 `RemoteConfigFetcher`**，而那正是第 4 節要講的自舉問題。

## 2. `ApplicationBase::run` — 固定五步骨架

`src/common/app/ApplicationBase.cc:49-74`，所有應用型別共用：

```cpp
int ApplicationBase::run(int argc, char *argv[]) {
  Thread::blockInterruptSignals();                   // ① 擋掉 SIGINT/SIGTERM
  auto parseFlagsRes = parseFlags(&argc, &argv);     // ② 解析 --xxx_config.* 前綴
  XLOGF_IF(FATAL, !parseFlagsRes, "Parse flags failed: {}", parseFlagsRes.error());
  folly::init(&argc, &argv);                         // ③ folly 初始化（吃剩下的 gflags）
  if (FLAGS_release_version) { ... return 0; }
  auto initRes = initApplication();                  // ④ 子類別實作，真正的啟動
  XLOGF_IF(FATAL, !initRes, "Init application failed: {}", initRes.error());
  auto exitCode = mainLoop();                        // ⑤ 阻塞等訊號
  memory::shutdown();
  stop();
  return exitCode;
}
```

只有第 ④ 步是虛函式，`TwoPhaseApplication` 與 `OnePhaseApplication` 的全部差異都在那裡。

### 2.1 為什麼第一件事是擋訊號

`Thread::blockInterruptSignals()`（`common/app/Thread.cc`）對呼叫執行緒 `pthread_sigmask(SIG_BLOCK, {SIGINT, SIGTERM})`。原始碼註解直接說明了原因：

```
Note: Blocked signals will be inherited by child threads.
Note: This is important to make, because Linux can direct a SIGINT to any thread that has a
handler registered; so we need this to make sure that only the main thread (and not the worker
threads) receive a SIGINT, e.g. if a user presses CTRL+C.
```

關鍵在「**訊號遮罩會被子執行緒繼承**」。啟動過程中會建立大量執行緒（光 `net::Server` 的兩個 `ThreadPoolGroup` 就是 8 個池），如果不先遮罩，Linux 可能把 Ctrl-C 投遞到任意一個工作執行緒，而那些執行緒沒有處理邏輯。

順序因此變成：

```
主執行緒遮罩 SIGINT/SIGTERM
   └─ 所有子執行緒在遮罩狀態下建立 → 全部繼承遮罩
        └─ mainLoop() 中主執行緒 unblock（ApplicationBase.cc:82）
             └─ 從此只有主執行緒收得到 Ctrl-C
```

`mainLoop()`（`ApplicationBase.cc:76-90`）：

```cpp
signal(SIGINT,  handleSignal);
signal(SIGTERM, handleSignal);
signal(SIGUSR1, handleSignal);
signal(SIGUSR2, handleSignal);
Thread::unblockInterruptSignals();
{
  auto lock = std::unique_lock(loopMutex);
  loopCv.wait(lock, [] { return exitLoop.load(); });
}
return exitCode.load();
```

**訊號處理器是到這一步才註冊的**，所以整個初始化期間 Ctrl-C 不會把進程打死在半路——它會被排隊到遮罩解除之後才遞送。

`handleSignal`（`:40-47`）只做最小工作：

```cpp
XLOGF(ERR, "Handle {} signal.", strsignal(signum));
exitLoop = true;
if (signum == SIGUSR2) exitCode = 128 + SIGUSR2;
loopCv.notify_one();
```

`SIGUSR2` 的特別待遇是給外部編排系統的訊號——用 `128 + signum` 的 shell 慣例回報「我是被這個訊號結束的」，讓上層能區分正常停機與被要求重啟。

### 2.2 三層 flag 前綴

`parseFlags` 是虛函式，兩種應用型別解析的前綴不同（`app_detail::parseFlags`，`Utils.cc:140-152`）：

| 前綴 | 對應配置 | TwoPhase | OnePhase |
|---|---|---|---|
| `--app_config.*` | `AppConfig`（nodeId） | ✅ | ✅ |
| `--launcher_config.*` | `LauncherConfig`（mgmtd 位址、IB 裝置） | ✅ | ❌ |
| `--config.*` | 主配置（服務本體） | ✅ | ✅ |

搭配的檔案級 flag 定義在兩個地方——這個分裂本身說明了層次：

`src/common/app/gflags.cc`（啟動框架專屬）：

```cpp
DEFINE_bool(release_version, false, "Display release version");
DEFINE_string(app_cfg, "", "Path to .toml config file which contains specific config to this node");
DEFINE_bool(dump_default_app_cfg, false, "Dump default app config to stdout");
DEFINE_string(launcher_cfg, "", "Path to .toml config file which contains launcher config");
DEFINE_bool(dump_default_launcher_cfg, false, "Dump default launcher config to stdout");
DEFINE_bool(use_local_cfg, false, "Use local config instead of remote config for bootstrap");
DEFINE_string(cfg_persist_prefix, "", "If not empty, dump the full config to prefix_timestamp whenever config is updated");
```

`src/common/utils/ConfigBase.cc:13-15`（配置系統本身，與啟動框架無關）：

```cpp
DEFINE_string(cfg, "", "Path to .toml config file");
DEFINE_bool(dump_cfg, false, "Dump current config to stdout");
DEFINE_bool(dump_default_cfg, false, "Dump default config to stdout");
```

`--dump_*` 系列印出配置後直接 `exit(0)`（`Utils.cc:304-307`、`TwoPhaseApplication.h:38-41`），用來產生配置範本。注意 `--dump_default_cfg` 印的是**編譯進去的預設值**，`--dump_cfg` 印的是**套用全部來源後的最終結果**（`Utils.cc:294-297`），後者才是排查配置問題該用的那個。

分成三層是因為它們的**來源不同**：`app_config` 和 `launcher_config` 必然來自本地（否則無法引導），只有主配置可以來自 mgmtd。

前兩個前綴的解析實作在 `ServerLauncherBase::parseFlags`（`ServerLauncher.cc:4-10`），由 `TwoPhaseApplication::parseFlags`（`TwoPhaseApplication.h:28-33`）先呼叫，再自己解析 `--config.*`：

```cpp
Result<Void> parseFlags(int *argc, char ***argv) final {
  RETURN_ON_ERROR(launcher_->parseFlags(argc, argv));
  static constexpr std::string_view dynamicConfigPrefix = "--config.";
  return ApplicationBase::parseFlags(dynamicConfigPrefix, argc, argv, configFlags_);
}
```

### 2.3 三道啟動期硬性檢查

引導配置的兩個 `init()` 各只有十來行，但每個都藏了一道會讓進程直接 `FATAL` 的檢查。

**① nodeId 不得為 0**（`ServerAppConfig.cc:6-11`）：

```cpp
void ServerAppConfig::init(const String &filePath, bool dump, const std::vector<config::KeyValue> &updates) {
  auto res = ApplicationBase::initConfig(*this, filePath, dump, updates);
  XLOGF_IF(FATAL, !res, "Init app config failed: {}. ...", res.error(), filePath, dump);
  XLOGF_IF(FATAL, !allow_empty_node_id() && node_id() == 0, "node_id is not allowed to be 0");
}
```

`0` 是 `NodeId` 的無效值哨兵——`initCommonComponents` 就是靠 `nodeId == 0` 判斷要不要給監控指標加 `Node_N` 標籤（`Utils.cc:172-173`）。讓一個 nodeId 為 0 的節點註冊進叢集會造成身分衝突，所以擋在最前面。`allow_empty_node_id` 預設為 `true`（`ServerAppConfig.h`），正式部署應該關掉。

**② 開發版二進位拒絕啟動**（`ServerLauncherConfig.cc:7-14`）：

```cpp
void ServerLauncherConfig::init(const String &filePath, bool dump, const std::vector<config::KeyValue> &updates) {
  app_detail::initConfigFromFile(*this, filePath, dump, updates);
  auto rv = flat::ReleaseVersion::fromVersionInfo();
  if (!allow_dev_version() && !rv.getIsReleaseVersion()) {
    XLOGF(FATAL, "Dev version is not allowed: {}", rv);
  }
}
```

`allow_dev_version` 預設 `true`（`ServerLauncherConfig.h`），但生產環境的 launcher 配置設成 `false` 後，**任何非正式發布的二進位都無法啟動**。這道檢查排在整條鏈非常前面（`ServerLauncher.h:36`，早於 IB 初始化），所以誤把開發版部署上生產會立刻失敗而非跑到一半才出問題。

**③ mgmtd 的 NodeType 自檢**（`MgmtdConfigFetcher.cc:24`）：

```cpp
XLOGF_IF(FATAL, nodeType != flat::NodeType::MGMTD, "Unexpected NodeType: {}", static_cast<int>(nodeType));
```

見 §4——mgmtd 專用的 fetcher 若被餵進別的 NodeType，表示接線接錯了，寧可死掉。

這三道的共通模式是**啟動期一律 `FATAL` 而非回傳錯誤**：配置有問題的節點不該勉強啟動，交給編排系統重拉。與 §3.4 的重試策略同一個哲學。

## 3. `TwoPhaseApplication::initApplication` — 兩階段的邊界

`common/app/TwoPhaseApplication.h:38-70` 是整條鏈的核心。逐行拆：

```
Phase 1：Launcher（引導）
  ├─ [:42] launcher_->init()
  │     ├─ appConfig_.init(FLAGS_app_cfg, ...)              ServerLauncher.h:35
  │     ├─ launcherConfig_.init(FLAGS_launcher_cfg, ...)    ServerLauncher.h:36
  │     ├─ net::IBManager::start(launcherConfig_.ib_devices())  ServerLauncher.h:41
  │     └─ fetcher_ = make_unique<RemoteConfigFetcher>(launcherConfig_)  ServerLauncher.h:45
  │
  ├─ [:45] app_detail::loadAppInfo(...)      ← 先確定「我是誰」
  │
  └─ [:46] app_detail::initConfig(...)       ← 再拉配置（順序不可交換，見 3.2）

中間層：共用元件
  ├─ [:49] initCommonComponents()            ← log / waiter / monitor
  ├─ [:51] makeLogConfigUpdateCallback()     ← 讓 log 配置可熱更新
  ├─ [:52] makeMemConfigUpdateCallback()     ← 讓 jemalloc profiling 可熱切換
  └─ [:55] persistConfig()                   ← 落一份「當前生效配置」快照

Phase 2：Server（服務本體）
  ├─ [:58] initServer()
  │     ├─ server_ = make_unique<Server>(config_.server())  :92
  │     └─ server_->setup()                                 :93   ← bind
  ├─ [:63] startServer()
  │     └─ launcher_->startServer(*server_, appInfo_)        :99
  │           → server.start(appInfo) → beforeStart / group->start / afterStart
  └─ [:67] launcher_.reset()                 ← 引導設施退場
```

### 3.1 `IBManager::start` 為什麼在最前面

`ServerLauncher.h:41` 在讀完本地配置後立刻啟動 IB。`IBManager::startImpl`（`common/net/ib/IBDevice.cc:756-819`）做的事：

```cpp
if (!forkInited && config.fork_safe()) { ibv_fork_init(); forkInited = true; }   // :762-770
auto devices = IBDevice::openAll(config_);                                        // :773
eventLoop_ = EventLoop::create();  eventLoop_->start("IBManager");                // :787-788
socketManager_ = IBSocketManager::create();  eventLoop_->add(socketManager_, ...); // :791-795
devBgRunner_ = IBDevice::BackgroundRunner::create();                              // :796
for (const auto &dev : devices_) { /* 註冊 AsyncEventHandler、建 zone→port 對照 */ }
inited_ = true;
```

`ibv_fork_init()` 必須在**任何記憶體註冊之前、任何 fork 之前**呼叫——這是 libibverbs 的硬性要求，所以它排在整條鏈的最前段。

`config_.allow_no_usable_devices()`（`:778`）這個開關讓沒有 IB 卡的機器（開發環境、純 TCP 部署）也能起得來，只印 WARN。

### 3.2 為什麼 `loadAppInfo` 必須排在 `initConfig` 之前

這是整條鏈裡最容易忽略、但改動就會壞掉的順序約束。看 `app_detail::initConfig`（`Utils.cc:280-299`）：

```cpp
auto configTemplate = loadConfigTemplate(cfg, std::move(launcher));
XLOGF(INFO, "Full Config Template:\n{}", configTemplate);
auto renderRes = hf3fs::renderConfig(configTemplate, &appInfo);          // ← :286
XLOGF_IF(FATAL, !renderRes, "Render config failed: {}\nTemplate: {}", ...);
auto initRes = cfg.atomicallyUpdate(std::string_view(*renderRes), false);
auto res = cfg.update(updates, false);                                   // ← --config.* 覆寫最後套用
```

**mgmtd 下發的是配置模板，不是配置。** 同一份 `STORAGE` 模板要餵給叢集裡所有 storage 節點，裡面的 target 路徑、監聽位址、節點識別等欄位必須靠 `renderConfig(template, &appInfo)` 用該節點自己的 appInfo 展開。

所以順序是不可逆的：

```
loadAppInfo()   → 得到 nodeId / hostname / podname / clusterId / tags
       ↓ 這些值成為模板變數
initConfig()    → 拉模板 → render → atomicallyUpdate → 套用 --config.* 覆寫
```

同時注意最後一步：**命令列的 `--config.*` 覆寫在 render 之後才套用**，所以它永遠贏過 mgmtd 下發的值。這是運維手動介入的後門。

`AppInfo` 本身（`common/app/AppInfo.h`）分成兩層：

```cpp
struct FbsAppInfo : public serde::SerdeHelper<FbsAppInfo> {
  SERDE_STRUCT_FIELD(nodeId, NodeId(0));
  SERDE_STRUCT_FIELD(hostname, String{});
  SERDE_STRUCT_FIELD(pid, uint32_t(0));
  SERDE_STRUCT_FIELD(serviceGroups, std::vector<ServiceGroupInfo>{});
  SERDE_STRUCT_FIELD(releaseVersion, ReleaseVersion{});
  SERDE_STRUCT_FIELD(podname, String{});
};

struct AppInfo : FbsAppInfo {
  String clusterId;
  std::vector<TagPair> tags;
};
```

**只有 `FbsAppInfo` 那半是 serde 可序列化的**——它是心跳送給 mgmtd 的那部分。`clusterId` 與 `tags` 留在外層不參與序列化：`clusterId` 是連線前就得知道的引導參數（送給 mgmtd 沒有意義），`tags` 則是 mgmtd 下發給節點的，方向相反。

各欄位的填入時機分散在整條鏈上，這也是 §5.3 那條因果鏈存在的原因：

| 欄位 | 填入位置 |
|---|---|
| `nodeId` / `clusterId` | `buildBasicAppInfo`（`LauncherUtils.cc:9-20`），來自本地 `--app_config.node_id` |
| `hostname` / `pid` / `releaseVersion` | 同上，來自 `SysResource` |
| `tags` | `fetcher_->completeAppInfo()`，來自 mgmtd 或 FDB |
| `serviceGroups` | **`Server::start` 內部**（`Server.cc:37`），必須等 bind 完成 |
| `podname` | 只有 One-Phase 會填（`OnePhaseApplication.h:112`） |

最後一列是個真實的不一致：`buildBasicAppInfo`（`LauncherUtils.cc:10`）只呼叫 `SysResource::hostname()`，而該函式的預設參數是 `physicalMachineName = true`（`SysResource.h:13`），拿到的是實體機名。**Two-Phase 路徑全程沒有人填 `appInfo.podname`**，所以 mgmtd / meta / storage 心跳送出的 `podname` 一律是空字串；只有走 One-Phase 的 `monitor_collector` 與 `migration` 會明確呼叫 `hostname(false)` 填它（`OnePhaseApplication.h:106-112`）。

監控管線不受影響——`Monitor::start` 自己另外取了一次（`common/monitor/Monitor.cc:195-201`），所以指標標籤上的 podname 是對的。受影響的只有 mgmtd 節點表裡顯示的那一欄。

### 3.3 配置的三路來源

`loadConfigTemplate`（`Utils.cc:269-278`）決定模板從哪來，優先序寫得很直白：

```cpp
if (!FLAGS_cfg.empty()) {
  return loadConfigFromFile();          // ① --cfg 指定本地檔
} else if (FLAGS_use_local_cfg) {
  return cfg.toString();                // ② 用編譯進去的預設值
} else {
  return loadConfigFromLauncher(...);   // ③ 向 mgmtd 拉（正式部署路徑）
}
```

這三路直接決定了另一個開關（`TwoPhaseApplication.h:86`）：

```cpp

```

**只有走第 ③ 路的進程，才允許 mgmtd 事後推送配置更新。** 這是個安全閥：運維用 `--cfg` 手動指定配置除錯時，不希望 mgmtd 半路把它覆蓋回去。

`onConfigUpdated()`（`:88`）在每次配置更新後重新 `persistConfig`，所以本地磁碟永遠有一份「此刻生效的完整配置」快照。落檔路徑由 `--cfg_persist_prefix` 控制，帶微秒時間戳（`Utils.cc:177-192`），空值則跳過。

### 3.4 對 mgmtd 不可用的容忍：20 次指數退避

`loadAppInfo` 與 `loadConfigFromLauncher` 用完全相同的重試骨架（`Utils.cc:218-236` 與 `:238-260`）：

```cpp
auto retryInterval = std::chrono::milliseconds(10);
constexpr auto maxRetryInterval = std::chrono::milliseconds(1000);
for (int i = 0; i < 20; ++i) {
  auto res = launcher();
  if (res) { /* 成功，返回 */ }
  XLOGF(CRITICAL, "... failed: {}\nretryCount: {}", res.error(), i);
  std::this_thread::sleep_for(retryInterval);
  retryInterval = std::min(2 * retryInterval, maxRetryInterval);
}
XLOGF(FATAL, "Load ... failed, stop retrying");
__builtin_unreachable();
```

10ms 起步、倍增、封頂 1s、共 20 次，總等待上限約 **15 秒**，然後 `FATAL` 直接讓進程死掉。

這個取捨很明確：**啟動期拿不到配置就死，交給編排系統（K8s / systemd）重拉**，而不是帶著預設配置勉強跑起來。一個用錯配置的 storage 節點比一個沒起來的 storage 節點危險得多。

`hf3fs_fuse.cpp:22-35` 的 `withRetry` 是同一個模式的手抄版（同樣 20 次、10ms→1s），可見這是團隊的固定慣例。

### 3.5 `initCommonComponents` 與熱更新回呼

`Utils.cc:165-175`：

```cpp

XLOGF(INFO, "Init waiter singleton {}", fmt::ptr(&net::Waiter::instance()));
```

中間那行看似只是印日誌，實際目的是**強制初始化 `net::Waiter` 單例**。`Waiter` 管理所有進行中 RPC 的請求對應表，是全域單例；在此處主動觸發建構，避免第一個請求到來時才在多執行緒下競爭初始化。印出指標值則是為了在日誌裡能確認整個進程只有一份。

`makeMemConfigUpdateCallback`（`Utils.cc:196-214`）值得一提：它註冊的回呼會在配置熱更新時呼叫 `je_profiling()` 開關 jemalloc 的記憶體 profiling 並 dump heap 檔。也就是說，**線上可以透過 mgmtd 推一次配置更新，遠端對某個節點開啟記憶體剖析**，不必重啟。它對 jemalloc 的偵測是靠弱符號：

```cpp
__attribute__((weak)) void __attribute__((nothrow))
malloc_stats_print(void (*write_cb)(void *, const char *), void *je_cbopaque, const char *opts);
```

沒有動態連結 jemalloc 時 `malloc_stats_print == nullptr`，回呼直接 return。

## 5. Phase 2：`setup` / `start` 的時序切分

這一節是整條鏈裡設計最講究的部分。

### 5.1 執行緒池其實在建構子就起了

一個常見誤解是「`setup()` 建立執行緒池」。實際上 `net::Server` 的建構子（`common/net/Server.cc:11-21`）：

```cpp
Server::Server(const Config &config)
    : config_(config),
      tpg_("Svr", config_.thread_pool()),                       // ← :13
      independentTpg_("SvrI", config_.independent_thread_pool()) // ← :14
{
  auto serviceNum = config_.groups_length();
  groups_.reserve(serviceNum);
  for (auto i = 0ul; i < serviceNum; ++i) {
    auto &tpg = config_.groups(i).use_independent_thread_pool() ? independentTpg_ : tpg_;
    groups_.emplace_back(std::make_unique<ServiceGroup>(config_.groups(i), tpg));
  }
}
```

`ThreadPoolGroup` 的建構子（`ThreadPoolGroup.h:31-50`）在初始化列表裡直接建 4 個池：

```cpp
procThreadPool_(config.num_proc_threads(), name + "Proc", ...),
ioThreadPool_(config.num_io_threads(), name + "IO", ...),
bgThreadPool_(config.num_bg_threads(), name + "BG", ...),
connThreadPool_(config.num_connect_threads(), ..., NamedThreadFactory(name + "Conn")),
```

所以 `new Server(config)` 那一刻，**兩組共 8 個執行緒池的執行緒就已經存在**。`ServiceGroup::start()` 裡的 `processor_.start()` / `ioWorker_.start()` 是把工作**排上**這些既有的池，不是建執行緒。

`ThreadPoolGroup` 還記錄了建構時的堆疊字串（`startStacktrace_`，`:33`），解構時若發現沒有先 `stopAndJoin` 會把它印出來（`:54-55`）——這是為了追查「哪個 ThreadPoolGroup 洩漏了」而付出的常駐記憶體代價。

### 5.2 `setup()` 做的唯一一件事：bind

`Server::setup()`（`Server.cc:23-32`）→ `ServiceGroup::setup()`（`ServiceGroup.cc:25-28`）→ `Listener::setup()`（`Listener.cc:62-114`），中間兩層都只是轉發加日誌包裝。

`Listener::setup()` 的實質內容分兩段。第一段選位址（`:63-88`）：

```cpp

  if (addr.up && (filters.empty() || filters.count(name) != 0) &&
      checkNicType(name, networkType_, config_.custom_tcp_nic_prefix())) {
    addressList_.push_back(Address{addr.ip.toLong(), config_.listen_port(),
                                   networkType_ == Address::LOCAL ? Address::TCP : networkType_});

```

掃全部網卡，依三個條件過濾：介面 up、在 `filter_list` 白名單內（空則不限）、網卡型別符合本 group 宣告的 `network_type`。**一個 group 可以同時監聽多張網卡**——多 IP 主機上 `addressList_` 會有多筆。

第二段建 socket（`:93-113`）：

```cpp

  auto evb = connThreadPool_.getEventBase();
  auto createSocket = [&]() -> CoTask<folly::coro::ServerSocket> {
    co_return folly::coro::ServerSocket(folly::AsyncServerSocket::newSocket(evb),
                                        address.toFollyAddress(),
                                        config_.listen_queue_depth(),
                                        config_.reuse_port());

    address.port = socket->getAsyncServerSocket()->getAddress().getPort();   // ← :110
  }

```

`folly::coro::ServerSocket` 的建構子完成 `bind()` + `listen()`，但**還沒有人在 `accept()`**。

`:110` 那行是這整個設計的關鍵：配置寫 `listen_port: 0` 時由核心分配埠號，**必須 bind 完才知道自己在哪**，所以要把真實埠號回填進 `addressList_`。

註解 `// must create socket in evb thread` 也值得注意——folly 的 `AsyncServerSocket` 綁定 EventBase 執行緒，所以連建構都得 `scheduleOn(evb)` 再 `blockingWait`。

### 5.3 `Server::start` 的三段與 appInfo 因果鏈

`Server.cc:35-46`：

```cpp
Result<Void> Server::start(const flat::AppInfo &appInfo) {
  appInfo_ = appInfo;
  appInfo_.serviceGroups = getServiceGroupInfos();                    // ← :37
  RETURN_ON_ERROR_LOG_WRAPPED(INFO, "Server::beforeStart", beforeStart());  // ← :39
  for (auto &group : groups_) {
    RETURN_ON_ERROR_LOG_WRAPPED(INFO, desc, group->start());          // ← :42
  }
  RETURN_ON_ERROR_LOG_WRAPPED(INFO, "Server::afterStart", afterStart());
  return Void{};
}
```

把 `setup` 與 `start` 串起來看，因果鏈是這樣的：

```
  ① new Server(config)
       └─ 8 個執行緒池就緒
  ② setup()
       └─ 掃網卡 → bind() + listen() → 回填真實埠號
  ③ start()
       ├─ [Server.cc:37] appInfo_.serviceGroups = getServiceGroupInfos()
       │       ↑ 此刻位址才是確定的，因為 ② 已經 bind 完
       ├─ [Server.cc:39] beforeStart()
       │       ↑ 服務自己的組裝：建 mgmtd client、送第一次心跳、addSerdeService
       │         心跳裡帶的位址因此是真實可連的
       │         而且此時還沒有人 accept，不會有請求打到半初始化的 service
       └─ [Server.cc:42] group->start()
               ↑ 從這一刻起開始接受連線
```

**`beforeStart()` 是「已經占住埠號、但還沒開門」的那個窗口。** 這個窗口的存在，讓 3FS 能做兩件否則做不到的事：

1. 心跳送出的 `serviceGroups` 位址保證真實（`listen_port: 0` 的情況下尤其重要）。
2. 可以在窗口內做**任意長的阻塞協調**，見下一節。

### 5.4 `beforeStart` 的極致用法：storage 等自己下線

`StorageServer::beforeStart`（`StorageServer.cc:26-39`）最後一行是 `components_.start(appInfo(), tpg())`，而 `Components::start`（`Components.cc:39-69`）在第 60 行呼叫 `waitRoutingInfo`。

`Components::waitRoutingInfo`（`Components.cc:71-134`）裡有這樣一段（`:91-122`）：

```cpp
for (auto sleep = 0;; ++sleep) {
  if (sleep) {
    XLOGF(WARNING, "Waiting for target offline in routing info...");
    std::this_thread::sleep_for(1000_ms);
  }
  folly::coro::blockingWait(mgmtdClient.load()->heartbeat());
  auto copy = currentMap->clone();
  auto refreshResult = folly::coro::blockingWait(mgmtdClient.load()->refreshRoutingInfo(false));
  if (UNLIKELY(!refreshResult)) { XLOGF(ERR, ...); continue; }
  auto result = copy->updateRouting(mgmtdClient.load()->getRoutingInfo(), false);
  if (UNLIKELY(!result)) { XLOGF(ERR, ...); continue; }
  bool needWaiting = false;
  for (auto &[targetId, target] : copy->getTargets()) {
    if (target.publicState == flat::PublicTargetState::SERVING ||
        target.publicState == flat::PublicTargetState::SYNCING ||
        target.publicState == flat::PublicTargetState::WAITING) {
      XLOGF(WARNING, "waiting for chain {} target {}", targetId, serde::toJsonString(target));
      needWaiting = true;
      break;
    }
  }
  if (!needWaiting) break;
}
```

**一個重啟中的 storage 節點會卡在 `beforeStart()` 裡，每秒送一次心跳、拉一次 routing info，直到 mgmtd 確認它的所有 target 都已離開 SERVING / SYNCING / WAITING 狀態，才繼續啟動。** 這個迴圈沒有次數上限也沒有超時。

理由是 CRAQ 的正確性：如果一個剛重啟、本地資料可能落後的節點立刻開始服務讀請求，客戶端就可能讀到陳舊資料。必須先讓叢集把它從服務鏈上摘掉，走完 resync 流程再重新加入。詳見 [storage_main 報告](storage_main-存儲服務深度剖析.md) 與記憶中的 CRAQ target 狀態機。

這正是 `beforeStart()` 這個 hook 要存在的理由——它不是「初始化的最後一步」，而是**「對外服務前的准入檢查點」**，可以無限期地卡住。

### 5.5 `group->start()` 的四件事與 RDMA 的動態注入

`ServiceGroup::start()`（`ServiceGroup.cc:30-38`）：


第 ③ 項 `checkConnectionsRegularly`（`:48-55`）每 `check_connections_interval`（預設 60s）掃一次，把閒置超過 `connection_expiration_time`（預設 1 天）的連線回收。

第 ④ 項 `Listener::start`（`Listener.cc:118-145`）藏了一個容易錯過的動作：

```cpp

    XLOGF(CRITICAL, "Address::Type is RDMA, but IBDevice not initialized!");
    return makeError(RPCCode::kIBDeviceNotInitialized);
  }
  auto accept = [this](auto socket) { acceptRDMA(std::move(socket)); };
```

**一個 RDMA group 會被框架自動塞進一個走 TCP 的 `IBConnectService`。** 這是 3FS RDMA 設計的核心——RDMA 的 QP 握手需要一條頻外通道交換 GID / QPN / PSN，3FS 選擇讓這條控制通道走 serde RPC over TCP。所以：

- `addSerdeService` 除了在 `beforeStart()` 被業務程式碼呼叫，**在 `group->start()` 期間還會被框架自己再呼叫一次**。
- 服務端實際註冊的 service 數量比你在 `beforeStart()` 裡寫的多一個。
- 這也是為什麼 `IBManager::start` 必須排在整條啟動鏈的最前面（`ServerLauncher.h:41`）——`Listener::start` 會檢查 `IBManager::initialized()`，沒初始化就直接失敗。

RDMA 握手細節見記憶中的「控制平面 TCP / 非對稱握手 / server 主動發起」筆記與 [hf3fs_common_shared 報告](hf3fs_common_shared-共用基礎設施深度剖析.md)。

真正的 accept 迴圈在 `:139-142`：

```cpp
for (auto &socket : serverSockets_) {
  ++running_;
  auto evb = socket.getAsyncServerSocket()->getEventBase();
  co_withCancellation(cancel_.getToken(), listen(std::move(socket))).scheduleOn(evb).start();
}
serverSockets_.clear();
```

每個監聽位址一個協程，socket 的所有權從 `serverSockets_` 移交給協程，vector 清空。這使得 `stopAndJoin` 必須靠 `running_` 計數而非 vector 大小來判斷是否停乾淨。

### 5.6 `addSerdeService` 的分派規則

`Server.h:42-52`：

```cpp
template <class Service>
Result<Void> addSerdeService(std::unique_ptr<Service> &&obj, bool strict = false) {
  for (auto &group : groups_) {
    if (group->serviceNameList().contains(std::string{Service::kServiceName})) {
      return group->addSerdeService(std::move(obj));
    }
  }
  if (strict) return makeError(RPCCode::kInvalidServiceName);
  return groups_.front()->addSerdeService(std::move(obj));
}
```

依 service 名字在各 group 的 `services` 配置清單裡找歸屬。`strict = true` 表示「找不到就報錯」，`false` 表示「找不到就丟進第一個 group」。

所有服務的寫法都一致（`simple_example/service/Server.cc:50-51`、`MetaServer.cc:64-65`、`StorageServer.cc:27-28`、`MgmtdServer.cc:33-34`）：

```cpp
RETURN_ON_ERROR(addSerdeService(std::make_unique<XxxService>(...), true));   // 業務服務：strict
RETURN_ON_ERROR(addSerdeService(std::make_unique<core::CoreService>()));     // 管理服務：非 strict
```

業務服務用 `strict` 是因為它必須落在正確的 group（通常是 RDMA 那個）；`CoreService` 用非 strict 是因為它在配置裡通常有明確歸屬（獨立執行緒池的 TCP group），退一步落到第一個 group 也不影響正確性。

### 7.1 觸發到退出

注意最外層的順序：**先停服務，再停監控，最後停 IB**。監控晚於服務停止，才能記錄到停機過程本身的指標；IB 最後停，因為服務停止過程中仍可能有 RDMA 操作要收尾。

### 7.2 `Server::stopAndJoin` 的逆序拆除

`Server.cc:48-64`：

```cpp
void Server::stopAndJoin() {
  if (stopped_.test_and_set()) {                                    // ← :49 冪等保護
    XLOGF(INFO, "Server {} is already stopped", fmt::ptr(this));
    return;
  }
  LOG_COMMAND(INFO, "Server::beforeStop", beforeStop());            // ← :54
  for (auto &group : groups_) {
    LOG_COMMAND(INFO, desc, group->stopAndJoin());                  // ← :58
  }
  LOG_COMMAND(INFO, "Server::afterStop", afterStop());              // ← :61
  LOG_COMMAND(INFO, "Stop tpg", tpg_.stopAndJoin());                // ← :62
  LOG_COMMAND(INFO, "Stop independentTpg", independentTpg_.stopAndJoin());
}
```

`stopped_` 是 `std::atomic_flag`，因為 `~Server()`（`Server.h:30`）也會呼叫 `stopAndJoin()`——顯式停機加解構的雙重呼叫必須冪等。

注意這裡用 `LOG_COMMAND` 而非 `RETURN_ON_ERROR_LOG_WRAPPED`：**停機路徑上任何一步失敗都不中斷後續步驟**，只記錄。這跟啟動路徑（任何一步失敗就整體失敗）是相反的策略，而且是對的——停機停到一半比完整停機更糟。

四個生命週期鉤子的完整對稱：

```
     start()                          stopAndJoin()
       │                                    │
   beforeStart()  ← 建依賴、註冊服務    beforeStop()   ← 通知業務準備停止
       │                                    │
   group->start() ← 開始 accept       group->stopAndJoin() ← 停止 accept 並排空
       │                                    │
   afterStart()                        afterStop()    ← 拆除依賴
```

實際用法對照：

| 服務 | `beforeStart` | `beforeStop` | `afterStop` |
|---|---|---|---|
| mgmtd | 組 `ServerEnv`、註冊服務、`mgmtdOperator_->start()` | — | `mgmtdOperator_.reset()` 停背景任務 |
| meta | 建 client、建 kvEngine、建 `MetaOperator`、註冊服務 | 停 mgmtdClient、停 backgroundClient | — |
| storage | 註冊服務、設協程池路由、`components_.start()`（含等待下線） | `reliableUpdate/Forwarding.beforeStop()` | `components_.stopAndJoin()` |
| simple_example | 建 client、建 storageClient、註冊服務 | 停 mgmtdClient、停 backgroundClient | — |

storage 是唯一四個鉤子用滿三個的——它有本地磁碟狀態要保護，`beforeStop` 先讓轉發層拒收新請求，`afterStop` 才在所有連線斷開後落盤收尾。

### 7.3 `ServiceGroup::stopAndJoin` 與 Listener 的等待

`ServiceGroup.cc:40-46`：

```cpp

```

`Listener::stopAndJoin`（`Listener.cc:147-171`）用忙等：

```cpp

  XLOGF(INFO, "Listener {} is waiting for {} tasks to finish...", fmt::ptr(this), r);
```

10ms 輪詢加日誌是刻意的——停機卡住時日誌會持續輸出「還有 N 個任務未結束」，方便定位。最後那段清理 UNIX domain socket 檔案，避免殘留檔案讓下次啟動 bind 失敗。

### 7.4 遠端 shutdown：完整閉環

`CoreService` 提供 6 個方法（`fbs/core/service/CoreServiceDef.h`，serviceId `10001`）：

```
echo(1) / getConfig(2) / renderConfig(3) / hotUpdateConfig(4)
getLastConfigUpdateRecord(5) / shutdown(6)
```

`shutdown` 的實作（`core/service/ops/ShutdownOperation.h:19-22`）：

```cpp
CoTryTask<ShutdownRsp> handle() {
  CO_RETURN_ON_ERROR(suicide(req_.graceful));
  co_return ShutdownRsp::create();
}
```

`suicide`（`common/utils/suicide.cc`）：

```cpp
Result<Void> suicide(bool graceful) {
  if (::kill(getpid(), graceful ? SIGTERM : SIGKILL) != 0) { ... }
  return Void{};
}
```

**遠端關機不是走另一條停機路徑，而是給自己發訊號，回到 7.1 的同一條路。** `graceful = false` 時直接 SIGKILL，完全不停機。

這解釋了為什麼 `CoreService` 通常被配置在一個**獨立執行緒池的 TCP group** 上（`simple_example/service/Server.h:51-54`）：

```cpp

c.groups(1).set_use_independent_thread_pool(true);
c.groups(1).set_services({"Core"});
```

業務流量把主執行緒池打爆時，管理面仍然連得上——才能推配置、才能遠端關機。這個雙埠模式 storage / meta / mgmtd 全部照抄。

## 8. 各服務 `beforeStart` 的現實：複製貼上

框架管到 `net::Server` 的生命週期為止。「要接哪些 client、註冊哪些 service」留給每個服務自己在 `beforeStart()` 裡寫——而且是**手抄的**。

`MetaServer.cc:26-43` 與 `simple_example/service/Server.cc:22-40` 前 19 行逐字相同：


三行 mgmtd 接線各自的作用：

| 呼叫 | 作用 |
|---|---|
| `setAppInfoForHeartbeat(appInfo())` | 心跳裡帶什麼——含 5.3 節確定的真實監聽位址 |

`blockingWait` 出現在協程程式碼裡是刻意的——`beforeStart()` 是同步介面（`Result<Void>`），而它必須在 accept 開始前完成，所以在這裡阻塞是正確的。

### 8.1 為什麼不抽象掉

這段重複不是疏忽。三個服務的依賴集合實際上不同：

```

```

要抽象成一個共用基底，就得引入「可選依賴」的機制（虛函式鉤子或 CRTP 特化），複雜度未必比 20 行複製貼上低。3FS 選擇讓 `src/simple_example/README.md` 成為那個「抽象」——新服務用 `cp -rf` + `sed` 產生，`src/migration/` 就是這樣來的：

```bash
find "src/$svr_name" "src/fbs/$svr_name" -type f | xargs sed -i "s/simple_example/$svr_name/g"
```

| 配置是模板而非成品 | `renderConfig(template, &appInfo)` 讓一份模板服務整類節點 | `loadAppInfo` 與 `initConfig` 產生不可交換的順序耦合 |
| 引導設施的壽命 | 用完即銷毀（`launcher_.reset()`） | mgmtd 需要 `if constexpr` 特例把 kvEngine 移交出來 |
| mgmtd 的自舉 | 獨立的 `MgmtdConfigFetcher` 直接讀 FDB | 兩套 fetcher 實作要平行維護 |
| bind 與 accept 分離 | `setup()` bind，`start()` accept | 多一層 API；但換來真實位址與 `beforeStart` 協調窗口 |
| `beforeStart` 的語意 | 「對外服務前的准入檢查點」，允許無限阻塞 | storage 重啟可能卡住數分鐘，且無超時 |
| 服務依賴的組裝 | 每個服務手抄 20 行，靠 `cp -rf` + `sed` 產生新服務 | 改動要同步四處；換來零抽象負擔 |
| fetcher 的可選能力 | `if constexpr (requires {...})` duck typing | 零成本，但可發現性差——不讀 `ServerLauncher.h:62` 就不知道有這條路 |
| 停機的錯誤處理 | `LOG_COMMAND` 記錄但不中斷 | 與啟動路徑策略相反；但停到一半更糟 |
| 訊號處理 | 主執行緒獨占，處理器晚註冊 | 初始化期間無法用 Ctrl-C 中斷 |
| 遠端關機 | RPC → `kill(self)` → 回到訊號路徑 | 只有一條停機路徑要維護與測試 |

## 0. 這份報告怎麼讀

現有的 17 份報告都是**按組件（binary）組織**的：`hf3fs_fuse_main` 講 FUSE 進程、`storage_main` 講存儲服務、`chunk_engine` 講 Rust 落盤引擎。這種切法對「理解一個模組」很好，但對「理解一個請求」很糟——一次 `read()` 會橫跨 5 個組件、3 個地址空間、至少 4 種執行緒模型，被切散在 5 份文件裡。

這份報告補的就是這個縫。它**不介紹模組**，它**跟著一個請求走**。組件內部的細節一律用「詳見 X 報告 §Y」帶過（最後一章有完整對照表），本文的價值全部集中在**銜接處**：

- 資料與控制權如何在層與層之間交接
- 每一跳做了什麼轉換（位址空間？位元組序？單位？）
- 哪裡是同步、哪裡是非同步、誰在哪個執行緒上跑
- 失敗在哪一層被吸收，哪一層才會讓使用者看到 errno

四條主線：

三個要點先講在前面，後面逐一驗證：

1. **資料平面的兩次 RDMA 都由 storage server 主動發起**。讀是 server 對 client 做 RDMA Write，寫是 server 對 client 做 RDMA Read。client 只在 RPC 裡遞交「位址 + rkey」，自己不 post 任何 RDMA WR。
2. **commit 沿著 RPC 回程倒著走**。TAIL 最先 commit，HEAD 最後 commit（`StorageOperator.cc:449` 的 `forwardWithRetry` 在 `:493` 的 `doCommit` 之前）。
3. **chunk→chain 的映射不存在任何地方**，是 client 每次 IO 現算的（`PioV::chunkIo` → `File::getChainId` → `Layout::getChainOfChunk`）。inode 裡只有 `tableId / tableVersion / chunkSize / stripeSize / (baseIndex, shuffle, seed)` 這幾個欄位。

## 2. 參與者：進程、執行緒、地址空間

### 2.1 三個地址空間

| # | 進程 | 持有什麼 | 註冊了什麼 RDMA 記憶體 |
|---|---|---|---|
| A | 使用者程式 | fd、使用者 buffer；④ 額外 mmap 了 iov shm 與 ioring shm | 無（註冊動作發生在 B） |
| B | `hf3fs_fuse` | inode 快取、MetaClient、MgmtdClient、StorageClient、RDMABufPool、iov 表 | ② ③ `RDMABufPool`（`FuseClients.cc:86`）；④ 使用者 iov 的每個 block（`Shm.cc:103`） |
| C | `storage_main` × N | TargetMap、BufferPool、chunk 儲存 | `BufferPool`（`BufferPool.cc:29`），4MB×1024 小緩衝 + 64MB×64 大緩衝 |

**關鍵交接**：④ 的 iov shm 同時被 A 與 B 映射；`ibv_reg_mr` 是 B 做的（B 有 IB 裝置 context），但寫進去的資料 A 直接看得到。這是 USRBIO 零拷貝的物理基礎。

註冊粒度值得單獨記一筆：`ShmBuf::registerForIO` 是**逐 block** 呼叫 `registerIOBuffer`（`src/lib/common/Shm.cc:102-117`），`block_size` 由使用者建立 iov 時指定，未指定就等於整個 iov 大小（`src/lib/common/Shm.cc:13`、`:35`）。因為每個 block 是獨立的 MR，一次 IO **不能跨 block 邊界**，`ShmBufForIO::memh` 直接擋掉：

```cpp
// src/lib/common/Shm.h:87-93
CoTryTask<storage::client::IOBuffer *> memh(size_t len) const {
  if (len && off_ / buf_->blockSize != (off_ + len - 1) / buf_->blockSize) {
    co_return makeError(StatusCode::kInvalidArg);
  }
  co_return (co_await buf_->memh(off_)).get();
}
```

另外，**ioring 本身的 shm 不註冊 RDMA**：`src/fuse/IovTable.cc:222` 明寫 `if (!iovaRes->isIoRing) { ... registerForIO ... }`，註解是 `io ring bufs don't need to be registered for ib io`。環是控制結構，資料在另一塊 iov 裡。

## 3. 主線① 掛載與開檔（控制平面）

### 3.1 掛載

`hf3fs_fuse` 起來後呼叫 `fuseMainLoop`（`src/fuse/FuseMainLoop.cc:9`），組出 fuse 參數並 `fuse_session_mount`。掛載參數裡有兩個對資料流有直接影響：

```cpp
// src/fuse/FuseMainLoop.cc:35-36
fuseArgs.push_back("-o");
fuseArgs.push_back(fmt::format("max_read={}", maxbufsize));   // = io_bufs.max_buf_size, 預設 1MB
```

連線建立時 `hf3fs_init` 再設一輪（`src/fuse/FuseOps.cc:342-347`）：

```cpp
conn->max_readahead = d.config->io_bufs().max_buf_size();
conn->max_read      = d.config->io_bufs().max_buf_size();
conn->max_write     = d.config->io_bufs().max_buf_size();
conn->max_background = d.config->max_background();      // 32
```

也就是說**核心送給 FUSE daemon 的單次讀寫上限就是 `io_bufs.max_buf_size`（預設 1MB）**，而 `RDMABufPool` 的每個緩衝也正好是這個大小（`FuseClients.cc:86`）。這兩個數字對齊不是巧合——`hf3fs_read` 直接把整個請求塞進一個 pool 緩衝，沒有分段邏輯。

`hf3fs_init` 同時會嘗試打開 splice 三件套（`FuseOps.cc:329-340`），這影響 §7 的複製計數，稍後再談。

### 3.2 lookup：路徑 → InodeId

`hf3fs_lookup`（`src/fuse/FuseOps.cc:644`）先攔截虛擬目錄（`/3fs-virt` 下的 `iovs`、`rm-rf`、`get-conf`，`:654-711`），這是 USRBIO 註冊 iov 的入口，主線④ 會用到。一般路徑走：

```cpp
// src/fuse/FuseOps.cc:714
auto res = withRequestInfo(req, d.metaClient->stat(userInfo, parent, name, false));
...
add_entry(res.value(), &e);                              // :722
if (d.userConfig.getConfig(userInfo).sync_on_stat()) {   // 預設 true
  flushAndSync(req, linux_ino(res.value().id), false, SyncType::Lookup, nullptr, &e);  // :724
}
```

`add_entry`（`:231-247`）把 `Inode` 塞進 `d.inodes` 這張 `unordered_map<InodeId, shared_ptr<RcInode>>`，並增 refcount。**`RcInode` 是後面所有 IO 的錨點**：它裝著 `inode`（含 layout）、寫緩衝 `writeBuf`、以及一整組長度版本狀態 `dynamicAttr`（`FuseClients.h:67-144`）。

注意 `sync_on_stat` 預設開著（`FuseConfig.h:80`），所以**每次 lookup 都可能觸發一次 meta sync RPC**。這是 3FS 為了讓 `ls -l` 看到正確長度付的代價。

### 3.3 open：session 與 O_TRUNC

```cpp
// src/fuse/FuseOps.cc:1449-1459
Uuid session;
if ((fi->flags & O_ACCMODE) == O_WRONLY || (fi->flags & O_ACCMODE) == O_RDWR) {
  session = meta::client::SessionId::random();
  auto res = withRequestInfo(req, d.metaClient->open(userInfo, ino, std::nullopt, session, fi->flags));
  ...
}
```

三個事實：

1. **唯讀開檔完全不打 meta**。`hf3fs_open` 只在寫模式下呼叫 `metaClient->open`；讀模式直接用 lookup 時快取的 inode。`MetaClient::open` 自己也再擋一層：`if ((flags & O_ACCMODE) == O_RDONLY) sessionId = std::nullopt;`（`src/client/meta/MetaClient.cc:638`）。
2. `direct_io` 旗標在這裡決定（`FuseOps.cc:1463-1466`）：`O_DIRECT`，或者 `enable_read_cache=false` 且非 `O_NONBLOCK`。這個旗標決定核心要不要把 read 回應塞進 page cache，直接影響 §7 的複製次數。
3. `O_TRUNC` 的截斷**不在 meta server 內完成**。meta 回一個 `needTruncate` 旗標，client 收到後自己跑 `truncateImpl`（`MetaClient.cc:593-609`），那是一連串對 storage 的 `removeChunks` + `truncateChunk`（`MetaClient.cc:894`、`:920`）。也就是說 `open(O_TRUNC)` 是一個**同步阻塞的、可能很長的分散式操作**，而不是一次 metadata 寫。

`fi->fh` 存的是 `new FileHandle{ptr, oDirect, session}`（`:1469`），後續每個 op 都用 `inodeOf(*fi, ino)` 從 fh 拿回 `RcInode`，避免查 map（`:417-422`）。

### 3.4 client 端現算 chunk → chain

這是整條路徑上最容易被誤解的一段，所以完整攤開。

**inode 裡存什麼**（`src/fbs/meta/Schema.h:140-144`）：

```cpp
SERDE_STRUCT_FIELD(tableId,      ChainTableId());
SERDE_STRUCT_FIELD(tableVersion, ChainTableVersion());
SERDE_STRUCT_FIELD(chunkSize,    ChunkSize(0));
SERDE_STRUCT_FIELD(stripeSize,   uint32_t(0));
SERDE_STRUCT_FIELD(chains,       (std::variant<Empty, ChainRange, ChainList>{}));
```

`ChainRange` 只有三個 32/8/64 位元欄位（`Schema.h:88-90`）：`baseIndex`、`shuffle`、`seed`。**沒有 per-chunk 對照表**。

**client 怎麼算**，三步：

```cpp
// ① 展開 chain index list（惰性，結果快取在 folly::DelayedInit）
// src/fbs/meta/Schema.cc:160-181
std::span<const uint32_t> Layout::ChainRange::getChainIndexList(size_t stripe) const {
  const auto &list = chains.try_emplace_with([&]() -> std::vector<uint32_t> {
    std::vector<uint32_t> chains(stripe);
    for (uint32_t i = 0; i < stripe; i++) chains[i] = baseIndex + i;
    switch (shuffle) {
      case NO_SHUFFLE: break;
      case STD_SHUFFLE_MT19937: hf3fs_shuffle(chains, seed); break;
      ...
    }
    return chains;
  });
  ...
}

// ② chunkIndex → chain index
// src/fbs/meta/Schema.cc:192-197
ChainRef Layout::getChainOfChunk(const Inode &inode, size_t chunkIndex) const {
  const auto chains = getChainIndexList();
  auto stripe = chunkIndex % stripeSize;
  return ChainRef{tableId, tableVersion, chains[stripe]};
}

// ③ offset → chunkIndex → ChainId
// src/fbs/meta/Schema.cc:75-91
Result<ChainId> File::getChainId(const Inode &inode, size_t offset,
                                 const flat::RoutingInfo &routingInfo, uint16_t track) const {
  auto ref = layout.getChainOfChunk(inode, offset / layout.chunkSize + track * TRACK_OFFSET_FOR_CHAIN);
  auto cid = routingInfo.getChainId(ref);
  if (!cid) return makeError(MgmtdClientCode::kRoutingInfoNotReady, ...);
  return *cid;
}
```

`TRACK_OFFSET_FOR_CHAIN` 定義在 `Schema.cc:20`，值 `7`，註解說 `it's best to be a prime number, so each track can start from different chains`。目前 FUSE 與 USRBIO 兩條路徑呼叫 `PioV::addRead/addWrite` 時 `track` 一律傳 `0`（`FuseOps.cc:1526`、`FuseOps.cc:457`、`IoRing.cc:172-173`），所以這個乘數在現行程式碼裡恆為 0。

**ChunkId 怎麼組**（`src/fbs/meta/Schema.cc:62-73`）：

```cpp
auto chunk = offset / layout.chunkSize;
if (chunk > uint32_max) return kFileTooLarge;
return ChunkId(id, 0, chunk);
```

`ChunkId` 是 16 位元組、**big-endian** 的固定佈局（`Schema.h:177-198`）：`[tenant:1][reserved:1][inode:8][track:2][chunk:4]`。big-endian 是為了讓字典序等於數值序——`ChunkId::range()`（`Schema.h:208-215`）就靠這點，用 `[（inode,0,chunkBegin), (inode,1,0))` 這個區間掃一個檔案的所有 chunk。

**三個推論**：

- 一個檔案的 chunk 只會落在 `stripeSize` 條 chain 上，chunk N 固定落在 `chains[N % stripeSize]`。
- 換言之，**同一個 chain 上該檔的 chunk 索引是 `stripe, stripe+stripeSize, stripe+2*stripeSize, ...`**。meta 算檔案長度時就利用這點：對每條 chain 各發一個 `queryLastChunk`，取 max（`src/fbs/meta/FileOperation.cc:97-124`）。
- `getChainIndexList` 的結果被 `folly::DelayedInit` 快取在 `Layout` 物件裡（`Schema.h:91`），而 `Layout` 又存在 `RcInode::inode` 裡，所以**同一個開啟的檔案只 shuffle 一次**。

### 3.5 chain → target → node

`ChainRef` 只到 chain index 為止，要變成真正的 `ChainId` 還得查 mgmtd 下發的 routing info：

```cpp

  auto [tid, tv, index] = ref.decode();
```


**`break` 與 `continue` 的差別在這裡是語意性的**：非 SERVING 就中斷整個掃描（CRAQ 鏈上一個節點掉了，它後面的節點資料也不可信）；trafficZone 不符只是跳過這一個（純粹是網路親和性過濾）。

| `LoadBalance` | 全域計數 + 執行緒內計數，挑負載最低的 node | **讀的預設**（`StorageClientImpl.cc:1648-1650`） |

**這裡有個值得記住的事實：3FS 的讀不強制走 TAIL。** 預設是 `LoadBalance`，任何 SERVING 副本都可讀。一致性靠 chunk 上的版本欄位保證——server 端 `ChunkReplica::aioPrepareRead` 會比對：

（走 chunk engine 的 target 不同：`ChunkEngine::aioPrepareRead` 把 `commitVer` 和 `updateVer` 都設成同一個 `meta.chunk_ver`（`src/storage/store/ChunkEngine.h:61-62`），所以上面那個分支恆不成立。chunk engine 是靠 copy-on-write 擋髒讀——`update_chunk` 產生新 chunk，但要到 `commit_chunk` 才寫進 `meta_cache` / RocksDB 讓 `get` 看得到，見 `src/storage/chunk_engine/src/core/engine.rs:481-510`。）

### 4.2 R3–R4：進 FUSE 前的兩件事

```cpp
// src/fuse/FuseOps.cc:1479-1495

```

**讀之前一定先把同一個 inode 的寫緩衝刷掉**。這是 3FS 對 read-after-write 的處理：寫緩衝只存在於本進程，storage 那邊看不到，所以讀之前必須落盤。注意這是**整個 inode 級別**的鎖（`pi->wbMtx`），不是 range 鎖——同一個檔案的讀寫在 FUSE 路徑上會互相串行化。

接著取緩衝：

```cpp

```

`d.bufPool` 是 `net::RDMABufPool::create(io_bufs.max_buf_size(), rdma_buf_pool_size())`＝1MB × 1024（`FuseClients.cc:86`、`FuseConfig.h:47,74`）。`RDMABufPool::allocate`（`src/common/net/ib/RDMABuf.cc:146-169`）先 `sem_.try_wait()`，free list 有就取，沒有才 `RDMABuf::allocate` 新配一塊並 `ibv_reg_mr`。**穩態下這裡不會有 `ibv_reg_mr`**，緩衝是重複使用的（`deallocate` 只把指標推回 free list，`:171-175`）。

池子耗盡時 `sem_.co_wait()` 會**阻塞這條 fuse 工作執行緒**（因為外層是 `blocking_wait`）。1024 個緩衝、256 條工作執行緒，正常不會撞到。

### 4.3 R5：`PioV::addRead` 切 chunk

```cpp

```

這不是複製，但是一次全量記憶體讀，計成本時要算進去。

`PioV::finishIo(true)` → `concatIoRes`（`PioV.cc:186-266`）負責把「N 個 chunk 的結果」摺回「M 個 iovec 的位元組數」。它做三件事：

1. **累加**：`res[iovIdx] += iolen`。
2. **偵測洞**：`if (iolen < io.length)` 就進入 hole 狀態，記下起點。
3. **處理洞**：如果 `read && allowHoles`，用 `memset` 把洞填零並把洞的大小補進 `res`（`:238-246`）；否則整個 iovec 回 `kHoleInIoOutcome`。

```cpp
// src/fuse/PioV.cc:225-233

  auto &hio = ios[*holeIo];
  memset(hio.data + holeOff, 0, hio.length - holeOff);
  for (size_t j = *holeIo + 1; j < i; ++j) memset(ios[j].data, 0, ios[j].length);
  res[iovIdx] += holeSize;
  inHole = false;
  holeIo = std::nullopt;

```

`kChunkNotFound` 在讀路徑被靜默忽略（`:216-218`），因為稀疏檔案就是會有 chunk 不存在。

最後：

```cpp

else            fuse_reply_buf(req, (char *)memh.data(), res[0]);
```

`fuse_reply_buf` 把 FUSE 進程緩衝裡的資料交回核心。`memh` 是區域變數，`fuse_reply_buf` 回傳後 `IOBuffer` 析構、緩衝回池。

### 5.1 兩段緩衝：`hf3fs_write` 的兩條分支


**直寫分支**（`:1592-1630`）：先把既有寫緩衝刷掉，然後


**攢批分支**（`:1632-1688`）：每個 inode 一塊獨立的 `write_buf_size`（預設 1MB，`FuseConfig.h:76`）緩衝，**第一次用到時才註冊**：

`registerIOBuffer` → `RDMABuf::createFromUserBuffer` → `ibv_reg_mr`（`StorageClient.cc:96-108`、`RDMABuf.cc:42-48`）。**這是一次真正的記憶體註冊，不是從池子取**，會有 pin memory 的成本。每個被寫過的 inode 各一塊。

攢批的條件很嚴格——**只接受嚴格連續的追加**：


### 5.2 `flushBuf`：唯一的寫入出口

四個呼叫點都匯到這裡（`src/fuse/FuseOps.cc:424`）：

`finishWrite`（`:2655-2669`）記錄長度提示：

### 5.4 CRAQ 鏈式轉發：每跳從前驅拉

`handleUpdate` 的第 4 步（`StorageOperator.cc:443-450`）：

```cpp

commitIO.commitVer = updateResult.updateVer;
commitIO.isRemove = req.payload.isRemove();

auto forwardResult = co_await components_.reliableForwarding
                         .forwardWithRetry(requestCtx, req, remoteBuf, chunkEngineJob, target, commitIO);
```

注意傳進去的是 `remoteBuf`——**HEAD 自己剛才那塊本地緩衝的 remote handle**。在 `doForward` 裡它被換進轉發請求：

```cpp
// src/storage/service/ReliableForwarding.cc:145-149
UpdateReq updateReq = req;
updateReq.options.fromClient = false;
updateReq.retryCount = retryCount;
updateReq.payload.rdmabuf = rdmabuf;                       // ← 換成前驅的緩衝
updateReq.payload.key.vChainId.chainVer = target.vChainId.chainVer;
```

於是後繼收到 `update` RPC 後跑同一套 `doUpdate`，它的 `updateIO.rdmabuf` 指向的是**前驅的記憶體**，`rdmaReadBatch` 就從前驅拉。**資料在鏈上流動的每一跳都是一次獨立的單邊 RDMA Read，發起方永遠是下游。**

```
client 緩衝 ──RDMA Read──► HEAD 緩衝 ──RDMA Read──► MID 緩衝 ──RDMA Read──► TAIL 緩衝
   (client 不參與)          (HEAD 不參與第二跳)      (MID 不參與第三跳)
```

`fromClient` 是 HEAD 身份的判定依據：

```cpp
// src/storage/service/StorageOperator.cc:338-341
if (UNLIKELY(req.options.fromClient && !target->isHead)) {
  co_return makeError(StorageClientCode::kRoutingError, "non-head node receive a client update request");
}
```

**兩個轉發時的例外**（§7.5 會再列一次）：

1. 如果 client 一開始就用了 `SEND_DATA_INLINE`，`updateReq = req` 會把 `inlinebuf` 整份複製下去，**整條鏈都走 inline**，沒有任何 RDMA。
2. 後繼處於 `SYNCING` 狀態且這次是部分寫時（`ReliableForwarding.cc:158-160` 的 `readForSyncing`），前驅會**先把整個 chunk 從自己磁碟讀進緩衝**再轉發整塊；若讀出來的長度 `<= max_inline_forward_bytes` 還會 memcpy 成 inline（`:210-213`）。

### 5.5 commit 沿 RPC 回程倒著回來

`handleUpdate` 的順序是：`doUpdate`（`:394`）→ `forwardWithRetry`（`:449`）→ `doCommit`（`:493`）。TAIL 沒有後繼，`forward` 立刻回 `kNoSuccessorTarget`（`ReliableForwarding.cc:113-117`），所以：

```
時間 →

HEAD:  doUpdate(DIRTY) ──── forward ─────────────────────────────► doCommit(COMMIT) ─► 回 client
                              │                              ▲
MID:                          └─ doUpdate(DIRTY) ─ forward ──┼──► doCommit(COMMIT) ─┘
                                                    │        ▲
TAIL:                                               └─ doUpdate(DIRTY) ─► doCommit ─┘
                                                       (無後繼，立刻)     ← 最先 commit
```

commit 版本一致性有兩道檢查：

```cpp
// src/storage/service/StorageOperator.cc:451-458
if (UNLIKELY(commitIO.commitVer != updateResult.updateVer)) {
  ... co_return makeError(StorageCode::kChunkVersionMismatch, ...);
}
// :480-487 checksum 對比
} else if (forwardResult.checksum != updateResult.checksum) {
  ... co_return makeError(StorageClientCode::kChecksumMismatch, ...);
}
```

`forwardResult.checksum` 是後繼算的、`updateResult.checksum` 是本地算的。**每一跳都會比對前後兩份 checksum**，不一致就整條失敗。`ReliableForwarding.cc:264-277` 更進一步：如果後繼回報 checksum 不符，前驅會重算自己緩衝的 checksum，若連自己的緩衝都對不上（代表本地記憶體被寫壞），直接 `ApplicationBase::handleSignal(SIGUSR2)` 自殺。

**寫入的冪等性**由 channel 機制保證（`ReliableUpdate.cc:16-127`）。client 為每個 write op 配一個 `(ChannelId, seqnum)`（`UpdateChannelAllocator.cc:39-63`），server 端以 `(clientId, chainId, channelId)` 為 key 快取上一次結果：

| 條件 | 行為 | 行號 |
|---|---|---|
| `channel.id == 0` | `kFoundBug`（不該發生） | `:29-36` |
| channel 正被別的請求鎖住 | `kChannelIsLocked` → client 端映射成 `kResourceBusy` → 重試 | `:56-61` |
| `seqnum < 快取的 seqnum` | `kDuplicateUpdate`（過期重送） | `:65-69` |
| `seqnum == 快取 && generationId 相同 && 有成功結果` | **直接回快取結果，不重做寫入** | `:72-98` |
| 其他 | 跑 `handleUpdate` 並更新快取 | `:112-123` |

### 5.6 長度一致性：`VersionedLength` 的三段旅程

檔案長度是這條路徑上唯一沒有「權威即時值」的東西——storage 只知道 chunk 有多長，meta 只在被通知時才更新，client 手上是個提示。

**第一段：client 本地提示**。`RcInode::DynamicAttr` 有四個計數器（`FuseClients.h:69-79`）：

```cpp
uint64_t written = 0;   // finishWrite 每次 ++
uint64_t synced  = 0;   // 週期 sync 推進
uint64_t fsynced = 0;   // fsync/close/truncate 推進
std::optional<meta::VersionedLength> hintLength;
```

`sync()`（`FuseOps.cc:517-549`）先看 `syncver >= writever` 就直接跳過（`:525-528`），沒有新寫入就不打 RPC。

**第二段：送給 meta**。

```cpp
// src/fuse/FuseOps.cc:529-533
auto hint = (fsync && (force || !d.config->fsync_length_hint()))
              ? std::optional<meta::VersionedLength>()      // 不帶提示 → 逼 meta 去查
              : guard->hintLength;
auto res = co_await d.metaClient->sync(userInfo, inode.inode.id, true, atime, mtime, hint);
```

`fsync_length_hint` 預設 `false`（`FuseConfig.h:32`，註解 `// for test`），所以**`fsync` 預設不帶長度提示，強制 meta 向 storage 查真實長度**；週期 sync 則帶提示，走快路徑。

**第三段：meta 決定**（`src/meta/store/ops/BatchOperation.cc:260-299`）：

```cpp
auto currLength = inode.asFile().getVersionedLength();
if (hintLength && !config().ignore_length_hint()) {
  if (currLength.truncateVer >= hintLength->truncateVer && currLength.length >= hintLength->length)
    co_return currLength;                                   // 提示比現值小，不用動
  if (hintLength->truncateVer == currLength.truncateVer && hintLength->length > currLength.truncateVer)
    co_return *hintLength;                                  // 直接採信提示
  ...
}
auto length = co_await fileHelper().queryLength(flat::UserInfo(user_), inode);   // :297 打 storage
```

`queryLength` 最終落到 `FileOperation::queryChunksByChain`（`src/fbs/meta/FileOperation.cc:78-179`）：對該檔佔用的每條 chain 各發一個 `queryLastChunk`，用 `chunkId.chunk() * chunkSize + lastChunkLen` 算出長度，取所有 chain 的最大值。

**close 的路徑**（`FuseOps.cc:551-576`）：`updateLength = (written > fsynced)`，有新寫入才要求 meta 重算。

一個容易踩的細節：**`hf3fs_release` 不刷寫緩衝**（`:1737-1774`，只在 `wb->len == 0` 時把緩衝釋放）。刷緩衝發生在 `hf3fs_flush`（`:1704`），而 `flush` 是 `close(2)` 時核心送的 `FUSE_FLUSH`，`release` 是 fd 引用歸零後才送的。順序上 flush 先於 release，所以正常關檔沒問題；但如果 flush 失敗，release 不會補救。

## 6. 主線④ USRBIO 旁路路徑

### 6.1 註冊三件事

USRBIO 要跑起來，使用者程式得先建立三種對應關係。全部走 **symlink 進虛擬目錄** 這個奇特但有效的通道。

**① 資料緩衝 iov**（`src/lib/api/UsrbIo.cc:109-183`）：

```cpp
auto p = fmt::format("/hf3fs-iov-{}", hf3fs::Uuid::random());
shm = new hf3fs::lib::ShmBuf(p, size, block_size, numa, ...);       // shm_open + mmap
auto target = hf3fs::Path("/dev/shm") / p;
auto link = fmt::format("{}/3fs-virt/iovs/{}{}{}{}{}{}", hf3fs_mount_point, shm->id.toHexString(),
                        block_size ? fmt::format(".b{}", block_size) : "", ...);
auto lres = symlink(target.c_str(), link.c_str());
```

symlink 的**檔名本身就是參數編碼**：`<uuid>[.b<blockSize>][.r<ioDepth>|.w<ioDepth>][.p<h|l>][.t<timeout>][.f<flags二進位>]`。FUSE 端 `IovTable::parseKey`（`src/fuse/IovTable.cc:28-111`）逐段解析。

FUSE 端收到 `hf3fs_symlink` 且父目錄是 `iovs` 時（`FuseOps.cc:1215-1219`）呼叫 `IovTable::addIov`（`IovTable.cc:124`），做三件事：`shm_open` + `mmap` 同一塊共享記憶體到自己的地址空間（`:171-198`）、逐 block `registerIOBuffer`（`:223` → `Shm.cc:102-117`）、登記進 `shmsById`（`:232-234`）。

**② IO 環 ior**：同一個 `hf3fs_iovcreate_general`，但 `is_io_ring=true`。差別在 FUSE 端**不註冊 RDMA**（`IovTable.cc:222`），且會額外建一個 `IoRing` 物件掛進 `IoRingTable`。

環的記憶體佈局（`src/fuse/IoRing.h:93-103`）：

```
buf +0                      : sqeHead (int32, atomic)
    +n                      : sqeTail
    +2n                     : cqeHead
    +3n                     : cqeTail          （n = ringMarkerSize()，對齊過的 4）
    +4n                     : IoArgs[entries]  ← 實際 IO 參數
    +4n+entries*sizeof(IoArgs): IoCqe[entries]
    ...                     : IoSqe[entries]
    ...                     : sem_t            ← cqe 完成通知
```

`IoArgs` 就是一次 IO 的全部描述（`IoRing.h:17-27`）：`bufId[16]`（哪個 iov）、`bufOff`、`fileIid`、`fileOff`、`ioLen`、`userdata`。**注意沒有指標**——全部是 id + 位移，因為兩個進程的虛擬位址不同。

**③ 檔案註冊**（`UsrbIo.cc:558-596`）：

```cpp
struct statx stx;
statx(fd, "", AT_EMPTY_PATH | AT_STATX_DONT_SYNC, STATX_INO, &stx);
auto dupfd = dup(fd);
auto regfd = std::make_shared<Hf3fsRegisteredFd>(fd, dupfd, hf3fs::meta::InodeId{stx.stx_ino}, status);
```

**`st_ino` 直接就是 3FS 的 `InodeId`**。所以 USRBIO 提交 IO 時只送 `fileIid`，FUSE 端用它查 `d.inodes` 這張表（`FuseClients.cc:278-295` 的 `lookupFiles`）。這也意味著**檔案必須先用普通 `open(2)` 開過**（走完主線①），USRBIO 才有東西可查。

### 6.2 提交與喚醒

提交端純粹是記憶體操作（`UsrbIo.cc:616-670`）：

```cpp
auto idx = ring.slots.alloc();                    // 從空閒槽位取一個
if (!idx) return -EAGAIN;
auto &args = ring.ringSection[*idx];
memcpy(args.bufId, iov->id, sizeof(iov->id));
args.bufOff  = p - iov->base;
args.fileIid = regfd->iid.u64();
args.fileOff = off;
args.ioLen   = len;
args.userdata = userdata;
ring.addSqe(*idx, userdata);                      // IoRing.h:133，原子推進 sqeHead
```

`hf3fs_prep_io` **不做任何 syscall**。真正的通知是 `hf3fs_submit_ios` 的一次 `sem_post`（`UsrbIo.cc:678`）。

FUSE 端 `watch` 執行緒（`FuseClients.cc:369-401`）：

```cpp
sem_timedwait(iors.sems[prio].get(), &ts);          // ts = now + jitter
do {
  gotJobs = false;
  auto n = iors.ioRings->slots.nextAvail.load();
  for (int i = 0; i < n; ++i) {
    auto ior = iors.ioRings->table[i].load();
    if (ior && ior->priority == prio) {
      auto jobs = ior->jobsToProc(config->max_jobs_per_ioring());   // 32
      for (auto &&job : jobs) { gotJobs = true; iojqs[prio]->enqueue(std::move(job)); }
    }
  }
} while (gotJobs);
```

`sem_timedwait` 有超時（`submit_wait_jitter` 預設 1ms，`FuseConfig.h:70`），所以**即使沒有 `sem_post` 也會定期掃一遍**——semaphore 是加速手段而不是唯一通道。

`jobsToProc`（`IoRing.cc:15-65`）決定一次撈多少：

| `ioDepth` | 行為 |
|---|---|
| `> 0` | 嚴格湊滿 `ioDepth` 個才處理，湊不滿就等 |
| `== 0` | 有多少拿多少 |
| `< 0` | 目標 `-ioDepth` 個；不足時等到 `timeout` 到期再處理（`:36-45`） |

負值配 timeout 是「盡量湊批但不無限等」的模式，計時器狀態存在 `lastCheck_`。

### 6.3 匯流點：`IoRing::process`

```cpp
// src/fuse/IoRing.cc:105-177
std::vector<std::shared_ptr<RcInode>> inodes;
lookupFiles(inodes, ringSection, sqeSection + spt, std::min(toProc, entries - spt));
if ((int)inodes.size() < toProc) lookupFiles(inodes, ringSection, sqeSection, toProc - (int)inodes.size());

std::vector<Result<lib::ShmBufForIO>> bufs;
lookupBufs(bufs, ...);                                    // 同樣分兩段處理環繞

lib::agent::PioV ioExec(storageClient, config.chunk_size_limit(), res);

for (int i = 0; i < toProc; ++i) {
  ...
  auto memh = co_await bufs[i]->memh(args.ioLen);         // 取該 block 的 IOBuffer
  if (!forRead_) {
    auto beginWrite = co_await inodes[i]->beginWrite(userInfo_, *metaClient, args.fileOff, args.ioLen);
    truncateVers[i] = *beginWrite;
  }
  auto addRes = forRead_
      ? ioExec.addRead (i, inodes[i]->inode, 0, args.fileOff, args.ioLen, bufs[i]->ptr(), **memh)
      : ioExec.addWrite(i, inodes[i]->inode, 0, args.fileOff, args.ioLen, bufs[i]->ptr(), **memh);
}
auto execRes = co_await (forRead_ ? ioExec.executeRead(userInfo_, readOpt)
                                  : ioExec.executeWrite(userInfo_, storageIo.write()));
ioExec.finishIo(!(flags_ & HF3FS_IOR_FORBID_READ_HOLES));
```

**這就是匯流點**。從 `PioV ioExec` 這一行開始，USRBIO 與 FUSE 走的是**完全相同的程式碼**：同樣的 `addRead/addWrite`、同樣的 `chunkIo` 切分、同樣的 `StorageClient::batchRead/batchWrite`、同樣的 RDMA。

唯一的差別是 `data` 指標指向哪裡：

| 路徑 | `data` | `buffer`(memh) |
|---|---|---|
| FUSE 讀/寫 | `memh.data() + off`（`RDMABufPool` 緩衝）或 `wb->buf` | 進程私有、進程自己註冊 |
| USRBIO | `bufs[i]->ptr()` = 使用者 shm 內的位址 | 使用者 shm 的該 block，FUSE 進程註冊 |

完成後回填 CQE（`IoRing.cc:230-271`）。這裡有段不太顯眼但重要的邏輯：多個 worker 可能並行處理同一個環的不同區段，所以 `sqeTail` 只能**按序**推進——`sqeProcTails_` 是已認領的尾巴佇列，`sqeDoneTails_` 是已完成但前面還沒完成的，只有輪到自己在隊首時才推進 `sqeTail`（`:238-257`）。

最後 `sem_post(cqeSem)`（`:271`）叫醒使用者的 `hf3fs_wait_for_ios`。取 CQE 端用 CAS 保證多消費者安全（`UsrbIo.cc:723-727`）。

### 6.4 USRBIO 省掉了什麼

| 段落 | FUSE 路徑 | USRBIO |
|---|---|---|
| syscall | `read`/`write` 各一次 | **0**（`prep_io` 純記憶體，`submit_ios` 只有 `sem_post`）|
| 核心 VFS + fuse.ko | 有 | **無** |
| /dev/fuse 佇列來回 | 有 | **無** |
| 使用者 ↔ 核心複製 | 1 次 | **0** |
| 核心 ↔ FUSE daemon 複製 | 1 次 | **0** |
| daemon 內 memcpy | 1 次（進 RDMA 緩衝） | **0**（資料本來就在已註冊的 shm 裡） |
| 每次 IO 一個請求 | 是 | 否，可攢批（`ioDepth`） |
| `PioV` → `StorageClient` → RDMA | 相同 | 相同 |

代價：使用者必須用 3FS 分配的 iov 當緩衝、必須先 `hf3fs_reg_fd`、單次 IO 不能跨 block 邊界、不滿足條件直接回 `-EINVAL`（`UsrbIo.cc:626-629`），**沒有退化成複製的 fallback**。

## 7. 表 A：資料被複製了幾次

計數規則：**「複製」指 CPU 執行的位元組搬移（memcpy / copy_to_user / copy_from_user）**。DMA（磁碟 → 記憶體、RDMA）不計為複製，但單獨標出來，因為它們仍然消耗記憶體頻寬。

### 7.1 讀路徑（FUSE，預設組態）

| # | 段落 | 機制 | CPU 複製 | 出處 |
|---|---|---|---|---|
| 1 | 磁碟 → server `localbuf` | io_uring `read_fixed` / libaio | **0**（DMA） | `AioStatus.cc:230` / `:102` |
| 2 | server `localbuf` → client `memh` | 單邊 RDMA Write | **0**（DMA） | `StorageOperator.cc:218`、`BatchReadJob.cc:81` |
| 3 | client `memh` → 核心 | `fuse_reply_buf` → writev(/dev/fuse) | **1** | `FuseOps.cc:1548` |
| 4 | 核心 → 使用者 buffer | 走 page cache 時多一次 `copy_to_user` | **0 或 1** | 由 `fi->direct_io` 決定，`FuseOps.cc:1463` |
| | **合計** | | **1～2** | |

第 4 行的不確定性來自：`direct_io=1` 時（`O_DIRECT`，或 `enable_read_cache=false` 且非 `O_NONBLOCK`）核心把回應直接落到使用者頁面；走 page cache 時要多一手。這一段在核心裡，3FS 唯一的控制點就是那個旗標。

### 7.2 寫路徑（FUSE，攢批分支，預設組態）

| # | 段落 | 機制 | CPU 複製 | 出處 |
|---|---|---|---|---|
| 1 | 使用者 buffer → 核心 fuse 請求 | `copy_from_user` | **1** | 核心 |
| 2 | 核心 → FUSE daemon | libfuse 讀 /dev/fuse | **1** | 核心 + libfuse |
| 3 | daemon 請求緩衝 → `wb->buf` | `memcpy` | **1** | `FuseOps.cc:1666` |
| 4 | `wb->buf` → HEAD 緩衝 | 單邊 RDMA Read | **0**（DMA） | `StorageOperator.cc:589` |
| 5 | HEAD 緩衝 → 磁碟 | `pwrite`（見下） | **0 或 1** | `ChunkFileView.cc:56-65` / `chunk.rs` |
| 6 | HEAD 緩衝 → MID 緩衝 | 單邊 RDMA Read | **0**（DMA） | `ReliableForwarding.cc:148` |
| 7 | MID 緩衝 → 磁碟 | 同 5 | **0 或 1** | |
| 8 | MID 緩衝 → TAIL 緩衝 | 單邊 RDMA Read | **0**（DMA） | |
| 9 | TAIL 緩衝 → 磁碟 | 同 5 | **0 或 1** | |
| | **合計（3 副本）** | | **3 + (0～3)** | |

**第 5/7/9 行的分歧點**，兩種儲存後端各有規則：

`ChunkStore`（傳統路徑，`ChunkFileView.cc:55-61`）：

```cpp
int fd = normal_;
if (size % kAIOAlignSize == 0 && offset % kAIOAlignSize == 0 &&
    reinterpret_cast<uint64_t>(buf) % kAIOAlignSize == 0) {
  fd = direct_;                       // O_DIRECT，DMA，0 次 CPU 複製
}
```

三者（長度、偏移、緩衝位址）**都** 4KiB 對齊才走 `O_DIRECT`；否則走 buffered fd，核心複製一次進 page cache。

`ChunkEngine`（Rust 路徑）：

- `safe_write` 對齊追加分支（`chunk.rs:200-234`）：直接 `pwrite(data, offset)`，**0 次**。
- `safe_write` 非對齊分支（`chunk.rs:235-268`）：`vec[offset..][..data.len()].copy_from_slice(data)`（`:256`）拼進 thread-local buffer 再整塊寫，**1 次**；若尾端未對齊還要先 `pread` 回來（`:248`）。
- `copy_on_write` 且 `skip_read && is_aligned_io`（`chunk.rs:133-138`）：直接寫新 chunk，**0 次**。
- `copy_on_write` 其他情形（`chunk.rs:139-150`）：先 `pread` 舊 chunk 進 buffer（`:115-121`），再 `copy_from_slice` 覆蓋（`:143`），再整塊寫，**1 次複製 + 1 次額外讀**。

`skip_read` 的條件是 `is_syncing || (offset == 0 && data.len() >= self.meta.len)`（`chunk.rs:112`）——**整塊覆寫才能省掉讀舊資料**。對齊判定函數在 `src/storage/chunk_engine/src/utils/aligned.rs:47-57`。

### 7.3 USRBIO 路徑

| # | 段落 | 機制 | CPU 複製 |
|---|---|---|---|
| 讀 1 | 磁碟 → server `localbuf` | io_uring | 0（DMA） |
| 讀 2 | server `localbuf` → 使用者 shm | 單邊 RDMA Write | 0（DMA） |
| | **讀合計** | | **0** |
| 寫 1 | 使用者 shm → HEAD 緩衝 | 單邊 RDMA Read | 0（DMA） |
| 寫 2 | HEAD 緩衝 → 磁碟 | `pwrite` | 0 或 1（同 §7.2 規則） |
| 寫 3~ | 鏈上各跳 | RDMA Read + pwrite | 每跳 0 或 1 |
| | **寫合計（3 副本）** | | **0 + (0～3)** |

USRBIO 讀路徑是真正的端到端零 CPU 複製：資料從磁碟 DMA 進 server 緩衝，再 RDMA 進使用者 shm，使用者程式直接讀 `iov->base + offset`。

### 7.4 三條路徑並排

```
FUSE 讀                     1(或2)        0          0      0(DMA)      —        1~2
FUSE 寫                       1           1          1      0(DMA)     0~1     3 + 0~3
USRBIO 讀                     0           0          0      0(DMA)      —         0
```

### 7.5 表 B：「零拷貝」宣稱的例外情境

3FS 的零拷貝宣稱在預設組態、對齊 IO、正常鏈狀態下成立。以下是**所有會破功的分支**，逐一附上判定條件與行號。

| # | 情境 | 判定條件 | 額外複製 | 出處 |
|---|---|---|---|---|
| 1 | **inline 讀** | `requestedBytes < max_inline_read_bytes`（預設 0，**關閉**） | server 端 `memcpy` 進回應 + client 端 `memcpy` 出來，各 1 次 | `StorageClientImpl.cc:706`、`BatchReadJob.cc:107`、`StorageClientImpl.cc:1715` |
| 2 | **inline 寫** | `writeIO->length <= max_inline_write_bytes`（預設 0，**關閉**） | client 端 `assign` 1 次；且整條鏈都走 inline | `StorageClientImpl.cc:1898-1901`、`ReliableForwarding.cc:145`（`updateReq = req` 複製 inlinebuf） |

| 5 | **未對齊落盤（ChunkStore）** | `size`/`offset`/`buf` 任一不是 4KiB 倍數 | 走 buffered fd，核心複製 1 次 | `ChunkFileView.cc:56-61` |
| 6 | **未對齊落盤（ChunkEngine）** | `!is_aligned_len(len) \|\| !is_aligned_len(offset) \|\| !is_aligned_buf(data)` | thread-local buffer 拼裝 1 次 | `chunk.rs:200`、`:235-268`；`utils/aligned.rs:47-57` |
| 7 | **部分覆寫觸發 COW 讀** | `!(is_syncing \|\| (offset==0 && len>=chunk.len))` | 先讀回舊 chunk（額外磁碟讀）+ `copy_from_slice` 1 次 | `chunk.rs:112-150` |
| 8 | **後繼在 SYNCING 且部分寫** | `isSyncing && (是 truncate/extend/部分 write)` | 前驅先讀整個 chunk 進緩衝（額外磁碟讀）；且長度 `<= max_inline_forward_bytes` 時再 `assign` 成 inline | `ReliableForwarding.cc:158-213` |
| 9 | **checksum 驗證** | 讀 `enableChecksum`（Release 預設 false，Debug 恆 true）；寫預設 true | 不是複製，但是一次全量記憶體讀 | `StorageClientImpl.cc:1723`、`:1881`、`ChunkReplica.cc:193` |
| 10 | **對齊讀放大** | `offset % 4096 != 0` 或 `(offset+len) % 4096 != 0` | 不是複製，但磁碟多讀最多 8KiB | `BatchReadJob.cc:20-21`、`:60-61` |
| 11 | **FUSE 路徑本身** | 走 `read(2)`/`write(2)` 而非 USRBIO | 讀 1~2 次、寫 3 次，見 §7.1/§7.2 | 架構固有 |

**結論**：零拷貝在 USRBIO + 4KiB 對齊 + 預設組態下是**端到端**成立的。FUSE 路徑上「零拷貝」只成立於**網路那一段**（client 緩衝 ↔ server 緩衝），前後兩端各有無法消除的複製。小 IO、未對齊 IO 在落盤那一跳會退化。跨 chunk 邊界**不會**破壞零拷貝——`PioV::chunkIo` 把它切成多個獨立的 `ReadIO`/`WriteIO`，每個各自指向 client 緩衝的一段連續區間，RDMA 分別搬（`PioV.cc:42-48`、`:83-92`）。

## 8. 表 C：每一跳的失敗會怎樣

### 8.1 錯誤分類機制

client 端把所有錯誤歸成三類（`StorageClientImpl.cc:137-174`）：

```cpp
isPermanentError:  kMemoryError, kInvalidArg, kChunkNotFound, kBadConfig, kProtocolMismatch,
                   kRequestCanceled, kReadOnlyServer, kNoSpace, kFoundBug, kChecksumMismatch
isTemporarilyUnavailable: kCommError, kTimeout, kRemoteIOError
isFastRetryError:  kRoutingVersionMismatch, kChunkNotCommit
```

- **permanent** → 立刻放棄，釋放 channel（`:1232-1233`）。
- **temporarily unavailable** → 重試，**並且**記進 `requestCtx.numFailures[(target,chain,ver)]`（`:1237-1240`、`:1246-1262`）。下一輪 `selectRoutingTargetForOps` 會把失敗次數 `>= max_failures_before_failover`（預設 1）的 target 濾掉（`:551-565`）——**一次失敗就換副本**。
- **fast retry** → 重試，但等待時間砍成 `init_wait_time / 2`（`:1242`）。

重試框架是指數退避（`:1149-1151`）：`init_wait_time=10s`、`max_wait_time=30s`、`max_retry_time=60s`（`StorageClient.h:363-365`）。`getWaitTime()` 回 0 就是總時間耗盡，把還沒完成的 op 標成 `kTimeout` 並放棄（`:1161-1182`）。

### 8.3 「哪一層吸收了失敗」的一句話總結

```
使用者只會看到：permanent 錯誤，或所有重試（60s）耗盡後的錯誤。

被完全吸收、使用者看不到的：
  · 單一副本失敗          → StorageClient 換副本（max_failures_before_failover=1）
  · chunk 髒讀            → fast retry（等待砍半）
  · routing 過期          → fast retry
  · 鏈上後繼掛掉/慢       → HEAD 自己重試 60s，期間 mgmtd 可能已把後繼移出鏈
  · 重複的寫請求          → channel 快取直接回上次結果
  · 稀疏檔案的空洞        → 填零，長度照算
  · 寫緩衝沒 flush        → 30s 背景 sync
  · close 失敗            → 背景 CloseTask 重試
```

## 9. 同步／非同步邊界與執行緒交接點

### 9.1 全路徑的同步點

```
① app: read(2)                    ── 同步阻塞（除非 O_NONBLOCK/AIO，3FS 不支援）
② kernel fuse.ko                  ── 同步等 daemon 回應
③ fuse 工作執行緒                  ── 同步：folly::coro::blockingWait
      FuseOps.cc:86-89
      template <typename Awaitable>
      auto withRequestInfo(fuse_req_t req, Awaitable &&awaitable) {
        auto guard = RequestInfo::set(req);
        return folly::coro::blockingWait(std::forward<Awaitable>(awaitable));
      }
      ★ 這是整條路徑上最重要的同步邊界：從這裡開始下面全是協程，
        但這條 OS 執行緒被占住直到協程完成。max_threads=256 就是併發上限。
④ StorageClient 協程               ── 非同步：co_await RPC、co_await 信號量
⑤ net client IO 執行緒             ── 事件驅動，IB CQ 輪詢
⑥ server serde 協程                ── 非同步
⑦ AioReadWorker / UpdateWorker     ── ★ 真正的 OS 執行緒，透過 BoundedQueue + Baton 與協程交接
⑧ 磁碟 io_uring                    ── 非同步，reap 時同步等
```

### 9.3 幾個併發細節

**批次內的併發**：讀是 `process_batches_in_parallel=true`（`StorageClient.h:393`），不同 node 的批次同時發；同一批內的所有 op 打包成**一個** `BatchReadReq`。寫則相反——同一 node 的多個 `WriteIO` 是**循序**送的（`StorageClientImpl.cc:1947`），因為 CRAQ 需要逐 chunk 序列化。

**chunk 級的鎖**：server 端每次 update 都要先鎖 chunk（`StorageOperator.cc:371-379`），拿不到就 `co_await lockGuard.lock()` 掛起協程。拿到鎖後**重新查一次 target**（`:383-387`），因為等鎖期間 chain version 可能變了。

**inode 級的鎖**：FUSE 路徑上 `pi->wbMtx` 是普通 `std::mutex`，在 `blockingWait` 期間一直持有（`FuseOps.cc:1482`、`:1590`）。**同一個 inode 的讀寫在 FUSE 路徑上會互相阻塞整條 OS 執行緒**。USRBIO 路徑不碰 `wbMtx`（它沒有寫緩衝），所以沒這個問題。

**`extendStripe` 的協程鎖**：`RcInode::extendStripeLock` 是 `folly::coro::Mutex`（`FuseClients.h:107`），只掛起協程不阻塞執行緒（`FuseOps.cc:2632`）。

## 10. 讀原始碼時發現的幾處值得記錄的東西

以下都是實際查證過的觀察，不是推測。列出來是因為它們會影響讀者對這條路徑的理解。

**① `PioV::checkWriteOff` 只有宣告沒有定義。** 標頭 `src/fuse/PioV.h:23-28` 宣告了它，註解說「if metaClient and userInfo are not nullptr, meta server will be contacted for latest file length」，但 `PioV.cc` 全檔沒有這個函數的定義，全 repo 也沒有呼叫點。

**② `PioV::trops_` 永遠是空的。** `PioV::executeWrite`（`PioV.cc:149-175`）有一整段處理 `truncateChunks` 失敗、重建 `wios_` 的邏輯，但 `trops_` 只在 `PioV.h:56` 宣告、`PioV.cc:133`（assert）和 `:149`（判空）出現，**沒有任何地方往裡面塞東西**。那 28 行是死程式碼。

**③ `PioV::potentialLens_` 寫了但沒人讀。** `PioV.cc:92`：

```cpp
bufOff += chunkLen;
potentialLens_[inode.id] = std::max(potentialLens_[inode.id], off + bufOff + chunkLen);
```

`bufOff` 已經加過 `chunkLen` 了又加一次，所以值本身也偏大。但全 repo 只有這一行寫、沒有任何地方讀（`PioV.h:57` 是唯一的另一處出現）。

**④ `BatchedOp::queryLength` 有一處疑似筆誤。** `src/meta/store/ops/BatchOperation.cc:276`：

```cpp
if (hintLength->truncateVer == currLength.truncateVer && hintLength->length > currLength.truncateVer) {
```

第二個比較拿 `length` 跟 `truncateVer` 比，從上下文看應該是 `currLength.length`。影響是**保守的**：條件為偽時會落到下面去打 storage 查真實長度（`:297`），結果仍然正確，只是多一輪 RPC。

**⑤ 讀取預設不走 TAIL。** 見 §3.5。很多 CRAQ 的介紹會說「讀走 tail」，3FS 不是——預設 `LoadBalance` 挑負載最低的副本，靠 `commitVer == updateVer` 判斷資料是否乾淨。

**⑥ inline IO 在預設組態下完全關閉。** `max_inline_read_bytes` / `max_inline_write_bytes` 的預設值是 `Size{0}`（`StorageClient.h:422-423`），且 repo 內所有 toml（`configs/hf3fs_fuse_main.toml`、`meta_main.toml`、`admin_cli.toml`、`hf3fs_client_agent.toml`）都明寫 `'0'`。讀的判定是 `requestedBytes < 0`（恆偽），寫的判定是 `length <= 0`（對非空寫恆偽）。所以談 3FS 的資料路徑時，inline 分支可以當成「存在但預設不啟用」。

**⑦ `hf3fs_release` 不刷寫緩衝。** 見 §5.6 末段。

**⑧ chunk engine 路徑不使用 io_uring 的 fixed file。** `ChunkEngine::aioPrepareRead`（`ChunkEngine.h:67-70`）只設 `state.readFd`，不設 `state.fdIndex`，所以 `IoUringStatus::collect`（`AioStatus.cc:236`）不會加 `IOSQE_FIXED_FILE`。`ChunkReplica` 路徑則會（`ChunkReplica.cc:71`）。兩者都用 fixed buffer（`state.bufferIndex` 一律有值）。

## 12. 一頁速查

```
開檔    open() → [唯讀: 只用 lookup 快取] / [可寫: meta open RPC + FileSession]
        inode 只存 {tableId, tableVersion, chunkSize, stripeSize, baseIndex, shuffle, seed}

定位    chunkIndex = offset / chunkSize
        chainIdx   = shuffled(baseIndex..baseIndex+stripeSize)[chunkIndex % stripeSize]
        ChainId    = routingInfo.chainTables[tableId][tableVersion].chains[chainIdx-1]
        ChunkId    = BE{[0][0][inode:8][track:2][chunk:4]}                  ← 16 bytes

讀      client 送 (chunkId, off, len, addr+rkey) → 任一 SERVING 副本
        server 4KiB 對齊讀盤 → subrange(head,len) → 單邊 RDMA Write 回 client
        回應只有長度 + checksum

寫      client 送 (chunkId, off, len, chunkSize, addr+rkey, checksum, channel) → HEAD
        每跳: 單邊 RDMA Read 從前驅拉 → pwrite → DIRTY → forward
        TAIL 無後繼 → commit → 回程逐跳 commit → HEAD 最後 commit → 回 client
        長度: client hint (VersionedLength) → meta；fsync 預設不帶 hint，逼 meta 查 storage

USRBIO  prep_io(純記憶體) → submit_ios(sem_post) → watch → ioRingWorker
        → 同一個 PioV → 同一個 StorageClient → RDMA 直接進/出使用者 shm

複製    FUSE 讀 1~2 次 | FUSE 寫 3 次 + 每副本 0~1 | USRBIO 讀 0 | USRBIO 寫 0 + 每副本 0~1
        破功條件: inline IO(預設關) / 填洞 / 未對齊落盤 / COW 部分覆寫 / SYNCING 轉發

重試    permanent(checksum, chunkNotFound, invalidArg…) → 不重試
        temporary(timeout, commError, remoteIOError)   → 重試 + 一次失敗就換副本
        fastRetry(routingMismatch, chunkNotCommit)     → 重試，等待砍半
        總預算 60s；轉發層 HEAD 另有獨立 60s 預算
```
